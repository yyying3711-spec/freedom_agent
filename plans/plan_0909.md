**任务：给 agent 一个目录，让它找出其中最长的 Python 文件，报告文件名、行数、以及该文件里定义了几个函数。**

准备环境（你手动做）：
```
sandbox/
  a.py        # 20 行，2 个函数
  b.py        # 80 行，5 个函数
  c.py        # 300 行，故意塞很多重复内容，超过截断预算
  notes.txt   # 干扰项
```

预期最优轨迹（4–5 步）：
1. `bash: ls sandbox` → 看到 4 个文件
2. `bash: wc -l sandbox/*.py` → 知道 c.py 最长
3. `read_file: sandbox/c.py` → **触发截断**，observation 末尾应带 `[truncated]` 标记
4. `bash: grep -c "^def " sandbox/c.py` → 模型意识到截断后改用 bash 数函数
5. Final Answer

验证清单，跑完看 trace 逐项打勾：

| 要求 | 怎么验 |
|---|---|
| 两个 tool 都能调 | trace 里同时出现 bash 和 read_file |
| 截断生效 | 第 3 步 observation 长度 ≤ 预算，且模型没有基于被截掉的内容瞎编 |
| 错误处理 | 单独再跑一次：故意让它 `read_file sandbox/d.py`（不存在），observation 应是错误信息，loop 继续而不是 crash |
| 正常退出 | 最终答案是 c.py / 300 行 / N 个函数，全对 |
| 兜底 | 把 max_steps 设成 2，确认它会强制停并报"步数耗尽" |

这个任务的好处是答案客观可核对，而且截断那步天然逼模型换策略——如果你的 harness 没把截断标记清楚，模型大概率会在第 3 步就直接乱答，一眼能看出问题。

做完这个再加难度：让它修改文件（写一个 `write_file` 或用 bash heredoc），验证 agent 能读→改→再读确认。
